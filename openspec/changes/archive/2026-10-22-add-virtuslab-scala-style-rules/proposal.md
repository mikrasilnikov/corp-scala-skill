# Proposal

## Why

Corporate Scala projects get their agent guidance from this repository's skills, which so far cover running the build (`sbt-launcher`) and one data-mapping task (`upickle`). Nothing tells an agent how to write the Scala itself: how to shape functions and files, how to model a domain, when a failure is an `Either` and when it is an exception. VirtusLab's `direct-style-scala` skill states exactly those rules, but binds them to one stack (sbt 2, Ox, Tapir, sttp, Magnum and more) and to Scala 3 only, and parts of it tell an agent to do what the corporate environment forbids: edit compiler flags in `build.sbt`, resolve dependency versions from Maven Central. A rules file that keeps the general rules and drops the stack can be loaded by OpenCode in every corporate Scala repository, on Scala 2.13 as well as 3, without contradicting the `sbt-launcher` skill.

## What Changes

- A new kind of deliverable beside skills: a rules file, plain Markdown meant to be loaded whole into an agent's context on every session (OpenCode's `AGENTS.md`, or a file listed under `instructions` in `opencode.json`), where a skill is loaded on demand. Rules files live directly under `rules/`, one file each, self-contained, without frontmatter.
- The first rules file, `rules/virtuslab-scala-style.md`: general Scala code style and domain modelling rules derived from VirtusLab's `direct-style-scala` skill (plugin version 1.0.11, Apache-2.0), in five groups: syntax and function shape; files, packages and visibility; domain modelling; error handling; test style. Roughly 100 to 150 lines, at most three short code examples, and a closing attribution line.
- Toolset references are omitted. The file names no build tool, formatter, library or framework: nothing about sbt, scalafmt, Ox, Tapir, sttp, jsoniter, PureConfig, MacWire, Magnum, Flyway, scalaxb, Kafka or OpenTelemetry. Scala and its standard library are language, not toolset, and stay. Upstream's chapters on project setup, resource management, background processes, concurrency, subprocesses, HTTP, persistence, email, streaming and observability are not carried over; the handful of general rules found inside them (converting generated types to domain types at the boundary, phantom-typed identifiers and proof types, opaque types kept in DTOs, configuration as per-module case classes with masked secrets, deterministic tests) are kept in the five groups. Three rules survive their mechanism: stream or page instead of materialising unbounded data; chain single-use values with `pipe` and `tap` from `scala.util.chaining`, which upstream imports from Ox; convert expected exceptions to values at the boundary, with the standard library instead of upstream's helper.
- Deliberate departures from upstream, each recorded in design: errors are sealed per module instead of one open application-wide type; rules are version-neutral, with the Scala 3 construct as the primary form and a Scala 2.13 equivalent for the four constructs that have none (braceless syntax, enums, opaque types, givens and extension methods); the repository's existing conventions and the formatter's output win over the syntax rules; the zero-warnings rule names no compiler flags and never asks the agent to edit build settings; the class-field `var` exception for actors is dropped; failing fast on invalid configuration at startup is named as the one sanctioned place a constructor throws; the reference project's naming habits (`_IN`/`_OUT`, `*Service`/`*Model`/`*Api`, `final class`) are not adopted.
- The root `README.md` gains a `## Rules files` section that lists the file with a one-line summary, gives the OpenCode install step, and states the convention for adding a rules file; its opening paragraph says the repository holds skills and rules files.
- Unchanged: both existing skills and their specs, the `skills/` convention, the archived changes, and `.claude/`. Nothing existing moves or changes meaning, so nothing is breaking.

## Capabilities

### New Capabilities

- `rules-collection`: how rules files are organised and installed: one plain-Markdown file per rules file directly under `rules/`, self-contained and without frontmatter, stating in its first lines what it applies to and what wins when it conflicts with a repository; the root README listing every rules file with a summary, the OpenCode install step, and the convention for adding one.
- `scala-code-style`: the syntax and function-shape rules an agent follows when writing Scala under the rules file: braceless Scala 3 syntax, explicit return types on public members, one concern per function, responsibilities split between named entities, chaining single-use values, explicit discards, streaming instead of unbounded materialisation, zero warnings under the repository's flags, targeted and deterministic tests, the Scala 2.13 equivalents, and the precedence of repository conventions on syntax.
- `scala-code-organisation`: where Scala declarations go: the narrowest visibility the call sites allow, file grouping decided by where a type is constructed, no grab-bag files, concept-named packages, no single-file packages, no sub-package shadowing a top-level definition, and companion objects as the home of a type's constructors and instances.
- `scala-domain-modelling`: how domain data is typed: immutable data with pure transitions, `var` confined to method bodies, immutable collections, lawful APIs with clock and id generation injected, invalid data unrepresentable, no raw primitives for domain concepts, smart constructors returning `Either`, two-case enums instead of Booleans, phantom-typed identifiers, proof types, generated and external types converted at the boundary, configuration as per-module case classes with masked secrets.
- `scala-error-handling`: the recoverable-or-unrecoverable decision rule, sealed per-module error types with typed cases, wrapping a callee's error in the caller's own type when crossing modules, composing validations as named steps, converting expected exceptions at the boundary with the most specific type, and bare `try`/`catch` reserved for defects at a processing loop's outermost boundary.

### Modified Capabilities

- `skill-collection`: the requirement "The root README lists every skill" changes so that the README states the repository is a collection of skills and rules files; the Rules files section it gains is specified by `rules-collection`. The two other requirements, on skill directories and self-containment, are unchanged: a rules file is not a skill directory.

## Impact

- Files: one new file, `rules/virtuslab-scala-style.md`; `README.md` edited in its opening paragraph and with one new section. No existing skill file changes.
- Downstream: a team adds the file to a project's `AGENTS.md`, or lists it under `instructions` in that project's `opencode.json`, and it then applies to every Scala change in that project. In a repository that also uses the `sbt-launcher` skill the two do not overlap: the rules file says nothing about running the build, formatting, or dependencies, and defers to the repository and its formatter on syntax.
- OpenSpec: five new capabilities and one modified. `openspec/specs/` stays flat (design D4 of the archived `multi-skill-layout` change); the four content capabilities are prefixed `scala-` so their owning rules file is clear.
- Source and licence: upstream is `https://github.com/VirtusLab/scala-skill`, path `direct-style-scala/skills/direct-style-scala/`, read at commit `2b4d8d0` of 2026-10-16, plugin version 1.0.11, `license: Apache-2.0` in its plugin manifest; the repository carries no LICENSE file. The rules file names its source and licence in a closing line, and its file name credits VirtusLab.
- Assumptions, recorded so review can overturn them: the file is installed per project, not globally, which is why it may assume a Scala codebase; one file is preferred over rules plus a separate examples file because everything in it is always in context; OpenCode's behaviour is as its rules documentation described it on 2026-10-20: `AGENTS.md` and every `instructions` file are concatenated into context, and file references inside them are not followed automatically.
- Verification is by text checks and review, as in the earlier changes, since nothing here is executable. The design lists the checks, including a search of the file for every omitted toolset name.
