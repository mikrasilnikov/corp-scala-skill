# Proposal

## Why

Corporate policy requires every Scala source change to be formatted with scalafmt, and every corporate repository ships the sbt-scalafmt plugin and a `.scalafmt.conf`; the skill says nothing about formatting, so an agent following it compiles and tests unformatted code, and nothing in it stops the agent from formatting through another tool or from reaching for the repository's scalafmt settings. The first change's proposal listed formatting among the corporate requirements to add later; now that the skill and the launcher carry their final name (`sbt-launcher`, archived change `2026-10-20-rename-to-sbt-launcher`), the rule is written once against that name.

## What Changes

- `skills/sbt-launcher/SKILL.md` gains a `## Formatting` section between "Running the build" and "Launcher-owned configuration". Every launcher invocation that compiles or tests begins with `scalafmtAll`, so the usual invocation becomes `./sbt-launcher.sh -batch scalafmtAll compile test`, and a change that ends without a build still gets `./sbt-launcher.sh -batch scalafmtAll` on its own. `scalafmtAll` is unscoped and run from the repository root, and the agent neither narrows nor replaces it: no `scalafmtOnly`, no `scalafmt` or `Test/scalafmt`, no `module/scalafmtAll` in its place, no skipping. Because the unscoped task reaches a module only through the root's aggregation, a changed module the root does not aggregate gets `<module>/scalafmtAll` right after it, in addition: `./sbt-launcher.sh -batch scalafmtAll core/scalafmtAll core/compile core/test`. Which files it touches is the repository's decision, made through `scalafmtFilter`, `scalafmtOnCompile`, and the `project.*` keys of `.scalafmt.conf`; files it reformats outside the agent's own edit stay formatted, and the agent says so when it reports. `scalafmtSbt` is not required. Formatting runs only through the launcher: no scalafmt CLI, no `cs launch scalafmt`, no Metals or IDE formatting. `.scalafmt.conf` and the scalafmt settings in the build definition are read-only.
- "When a build fails" gains a third after-the-marker stop-and-report case, **Formatting not available**: sbt rejecting a correctly spelled `scalafmtAll` (`Not a valid key`, `Not a valid command`) or the plugin reporting that `.scalafmt.conf` is missing. The agent does not add the plugin, create the file, format by other means, or continue unformatted. The own-mistake paragraph is amended so that a rejected, correctly spelled scalafmt task is not a typo to correct, the report template's area list gains `formatting`, its last line becomes `Changed before the stop: <...>` plus "I have not changed anything to work around this failure." so a stop after edits or reformatting reports truthfully, and a scalafmt parse error on a source file joins compile errors and failing tests as the agent's work. A failure to fetch the scalafmt version pinned in `.scalafmt.conf` is the existing "unresolved artifact" case; its message list gains the plugin's `scalafmt: [v<version>] failed to download`.
- The command-line allowlist row for sbt tasks adds `scalafmtAll` to its examples, the `bash` example block gains `./sbt-launcher.sh -batch scalafmtAll compile test`, and the frontmatter description names formatting and `.scalafmt.conf` so the skill triggers before an agent formats or touches scalafmt configuration.
- `skills/sbt-launcher/references/sbt-launcher.md` gains, in section 4, the formatting-not-available messages under "After the marker: stop-and-report exceptions", the scalafmt parse error under "After the marker: your work", and a row in the "Your own invocation mistakes" table that excludes a correctly spelled scalafmt task from the `Not a valid key` correction; and, in section 5, the formatting-first invocation and the non-aggregated module invocation among the worked examples, and the narrowed or substituted formatting and the module task in place of the unscoped one among the common mistakes. The messages it shows are real output from sbt 1.13.0 with sbt-scalafmt 2.6.2 and scalafmt 3.11.5, abbreviated, with a note that other versions word them differently.
- `README.md`: the skill's one-line summary gains formatting, since the `skill-collection` spec keeps that summary a condensation of the description.
- **BREAKING** for any repository that lacks the sbt-scalafmt plugin, its `scalafmtAll` task, or `.scalafmt.conf`: agents stop there and report, as they do for a missing launcher. Corporate policy requires both, so this makes a non-compliant repository visible rather than buildable. Also a visible change for every compliant repository: agents' builds now run `scalafmtAll` first, and where the repository has not narrowed the task's scope, an agent's diff may include reformatting of files it did not edit.
- Unchanged: every launcher and dependency rule; the `project-dependencies` capability, whose "Task needs an sbt plugin" scenario still holds (the agent does not add the plugin and tells the user; for scalafmt the message takes the stop-and-report shape, because the plugin is required of every repository rather than needed by the agent's task); the `launcher-owned-configuration` capability, because scalafmt settings are the repository owner's, not the launcher's, and are specified in the new capability; `skill-collection`; the archived changes.

## Capabilities

### New Capabilities

- `source-formatting`: the rule that every source change is formatted with scalafmt through the launcher: `scalafmtAll` first in every invocation that compiles or tests and on its own after a change with no build, unscoped from the repository root, never narrowed or replaced, with `<module>/scalafmtAll` added for a changed module the root does not aggregate; formatting scope left to the repository's scalafmt settings; `.scalafmt.conf` and the scalafmt build settings read-only; formatting only through the launcher; a missing plugin or configuration stopping the task; scalafmt parse errors as the agent's work.

### Modified Capabilities

- `sbt-invocation`: one requirement, "The agent corrects its own invocation mistakes", gains a scenario stating that sbt rejecting a correctly spelled scalafmt task is not an invocation mistake and is handled under `source-formatting`. Its SHALL statement and existing scenarios do not change, and the other ten requirements are untouched.

## Impact

- Skill files: `skills/sbt-launcher/SKILL.md` (143 lines) gains the Formatting section, the third stop-and-report item, two amended sentences in the failure path, one word in the report template, one task name in the allowlist row, one line in the `bash` example, and a longer description; it ends near 170 lines. `skills/sbt-launcher/references/sbt-launcher.md` (391 lines) gains two example blocks in section 4, one table row there, and one row in each of the two tables of section 5. All links stay as they are.
- `README.md`: the summary cell of the `sbt-launcher` row.
- Specs: one new main spec, `openspec/specs/source-formatting/spec.md`, created when the change is archived; one modified requirement in `sbt-invocation`, carried by this change's delta. The spec layout stays flat.
- Downstream: every agent session that loads the skill. Builds after a source change take the first-run cost of the plugin fetching the pinned scalafmt version through the launcher's repositories, which the existing "slow runs are not failures" rule already covers. Repositories decide scope: one that sets `scalafmtFilter` to `diff-dirty` sees only changed files reformatted; one that sets nothing sees everything unformatted reformatted on the agent's first build. A repository whose plugin predates `scalafmtAll` (sbt-scalafmt before 2.0.0-RC5) stops agents the same way as a missing plugin until the plugin is upgraded.
- Assumptions, recorded here so review can overturn them: `scalafmtAll` is run unscoped from the root rather than per module, so the repository's policy applies to every module the root aggregates, with `<module>/scalafmtAll` added only for a changed module it does not aggregate; files reformatted outside the agent's edit are left formatted and mentioned in the agent's report, never reverted; `scalafmtSbt` is not required, since the repository can enable formatting of the build definition itself, for example with `scalafmtSbtOnLoad` from sbt-scalafmt 2.6.2; the plugin's messages for a missing plugin, a missing `.scalafmt.conf`, a parse error, and an unfetchable version are quoted from one verified version and may be worded differently in others; the `source-formatting` capability keeps the flat spec layout and takes no skill prefix, like the three existing launcher capabilities.
- Verification: review and text checks as in every earlier change, plus a live run of sbt (1.13.0 and 2.0.11) with sbt-scalafmt 2.6.2 and scalafmt 3.11.5 in throwaway projects outside the repository, since no sbt project or launcher is available in it.
